## 1. 计划定位

本文件是后续工作的唯一总计划，只规定优先级、阶段边界和验收标准；本轮不生成分计划，也不实施代码、接口或数据库变更。

总体顺序为：**先让关键数据和图片真实可见，再调整首页与重点详情页，最后处理剩余页面。**

参考范围：

- 后端：`D:\Football-APP`
- 原型图：`C:\Users\hekmatyar\Desktop\足球APP`
- 需求文档：`D:\Football-APP\docs\references\product\tifo需求文档.pdf`

后续执行必须保护两个仓库中用户已有的未提交改动，不得用清库或覆盖式导入换取展示效果。

## 2. 当前结论与本轮重点

当前最影响客户端完成度的不是页面数量，而是以下三个问题：

1. **球员图片未正常显示**：数据库中的 `avatar_url` 虽大多非空，但部分指向需要鉴权的 `/uploads/**`，部分是 Flutter 当前不能直接显示的 SVG。
2. **发布内容封面未正常显示**：内容有封面字段，但仍存在访问权限、格式或 URL 解析问题，需从“数据库有值”升级为“客户端实际可见”。
3. **首页排布不符合原型**：推荐、资讯、比赛等卡片缺少明确的信息层级和适合各类型的版式，需要重做首页内容编排。

数据优先不是无限补数。本轮只建设足以支撑代表性原型页面的最小演示集，避免把工作扩张成完整数据平台。

## 3. 范围边界

### 3.1 本轮纳入

- 修复球员头像、球队 Logo、用户头像和内容封面的客户端显示链路；
- 补齐一场旗舰比赛的阵容、事件、统计、评分和关联内容；
- 补齐首页、数据页、球队/球员/比赛详情所需的最小文字数据；
- 重做首页推荐、资讯、比赛等内容的排布和视觉层级；
- 优先对齐首页、数据中心和足球详情等高频页面；
- 在杯赛数据页增加“淘汰树/总览”入口，进入后展示统一的“正在开发”占位页。

### 3.2 本轮明确不实现

- 手机号验证码；
- 一键手机号登录；
- 微信登录；
- 私信、聊天会话、IM；
- WebSocket 和 Push；
- 完整杯赛淘汰树的数据模型、管理能力和真实树形展示。

这些能力不得通过假接口或硬编码伪装为已经完成。

### 3.3 后续必须实施的独立专项

完整杯赛淘汰树是**后续必做功能**，不是永久排除项。当前后端仅有赛事、赛季、阶段、积分榜和排名能力，尚未发现能够表达淘汰赛对阵节点、主客场聚合、晋级关系及完整树形查询的业务模型/API。

因此后续需要单独制定后端专项，至少覆盖：

- 轮次、对阵节点及节点排序；
- 单场制/两回合制及总比分；
- 上一轮来源与下一轮去向；
- 晋级球队、待定球队和轮空状态；
- 按赛事与赛季查询完整淘汰树的接口；
- 管理端维护、数据校验及兼容策略。

本轮前端只建立稳定入口和占位路由，不提前虚构接口字段。

## 4. 四阶段执行顺序

| 阶段 | 目标 | 主要产出 | 完成门槛 |
| --- | --- | --- | --- |
| P1 | 图片与关键数据可见 | 可访问图片、内容封面、旗舰比赛和最小演示数据 | 真实 API 在客户端稳定呈现，不再主要依赖字母占位 |
| P2 | 首页优先对齐 | 推荐/资讯/比赛等卡片重新编排，公共视觉规则收敛 | 首页截图的结构、密度和视觉层级接近原型 |
| P3 | 足球重点页面对齐 | 数据中心、球队、球员、比赛详情；淘汰树入口与占位 | 重点页面使用 P1 数据完成主链路和视觉验收 |
| P4 | 剩余页面与总验收 | 内容、评论、发布、搜索、用户、通知、设置等 | 纳入页面有截图、测试和明确验收结论 |

依赖规则：

- P1 通过前不进行大规模页面视觉调整；
- P2 完成后再扩展公共样式到其他页面；
- 某页面数据不足时回到 P1 补齐，不允许在 Widget 中写死演示数据；
- 每次只执行一个分计划，验收未通过时只生成当前阶段修复计划。

## 5. P1：数据与媒体优化

### 5.1 最小演示数据集

优先复用当前已有对象，只补齐被原型和客户端实际使用的数据：

| 数据域 | 本轮目标 |
| --- | --- |
| 球队与球员 | 完善 2 支旗舰球队，每队至少 18 名球员；姓名、号码、位置合理 |
| 旗舰比赛 | 1 场已结束比赛，两队各 11 名首发、5—7 名替补，并有阵型、事件、统计和评分 |
| 首页内容 | 8—12 条文章/帖子/比赛/榜单等混合内容，均能进入对应详情 |
| 数据中心 | 至少 1 个联赛、1 个杯赛及可展示的赛程、积分和榜单数据 |
| 用户互动 | 1 个演示用户和少量作者、评论、点赞、收藏、关注及通知数据 |

球员头像可以多人复用同一张图片，内容封面也可复用少量图片；但文字、号码、位置、比分和关联关系必须合理。

### 5.2 图片可见性要求

- 第一批只准备少量 PNG/JPG/WebP：球员头像、队徽、用户头像和 3—6 张内容封面；
- 不再让匿名展示依赖会返回业务 401 的受保护 `/uploads/**`；
- 当前客户端不能显示的 SVG 优先转换或改指向 PNG/JPG，不因本轮补数扩大前端依赖；
- 图片地址必须在 Android 模拟器上返回 HTTP 200、正确的 `image/*` 类型且能被 Flutter 解码；
- 禁止直接热链不稳定的第三方图片；公开素材需保存来源和许可记录；
- 图片失败时仍保留统一占位，但占位不再作为正常数据的主要呈现方式。

### 5.3 数据安全与冲突规则

- 优先补齐已有 DEMO 记录和关联表，不重复创建同名球队、球员或比赛；
- 新数据使用独立的来源标记、自然键或保留 ID 范围，脚本必须可重复执行；
- 若旧 DEMO 冲突，可在记录原值后定向修改；非 DEMO 数据和真实用户数据不得覆盖；
- 写入前记录目标行和引用关系，写入后提供行数变化、校验结果和定向回滚说明；
- 禁止 `TRUNCATE`、全表删除、开发库整体重置和覆盖式历史 seed；
- 以现有 Backend V1 契约为准，补数阶段不擅自新增字段、枚举或接口。

公开文字和比赛数据可参考 [football-data.org](https://www.football-data.org/documentation/api) 或 [StatsBomb Open Data](https://github.com/hudl/open-data)；图片优先采用许可明确的 [Wikimedia Commons](https://commons.wikimedia.org/wiki/Commons:Reusing_content_outside_Wikimedia/licenses)，仅作演示仍需保留来源与许可信息。

### 5.4 P1 验收

- 球员头像、球队 Logo、用户头像和内容封面在客户端真实可见；
- seed 连续执行两次不重复增长、不修改非目标数据；
- 旗舰比赛两队各有 11 名首发，阵容、比分、事件、统计和评分一致；
- 首页、数据中心、球队、球员、比赛详情相关 API 有可展示响应；
- 现有接口路径、响应包装、枚举和分页语义保持兼容。

## 6. P2：首页排布优化

首页优先解决信息架构，不只调整颜色和圆角：

- 保留搜索、发布入口、频道 Tab、球队快捷入口和底部导航；
- “推荐”采用混合信息流，但不同卡片使用各自适合的结构；
- 图文资讯以双列卡片为主，突出封面、标题、作者和互动信息；
- 比赛、热评、讨论、榜单和球员评分使用全宽或专用卡片，不强塞进同一双列模板；
- “资讯”页突出内容时效、封面比例和摘要层级，与“推荐”形成明确差异；
- 比赛卡突出赛事、时间/比分、状态和双方队徽，减少无关信息；
- 保持后端 Feed 顺序和跳转语义，不在前端硬编码某支球队或固定新闻；
- 同步收敛字号、行高、间距、卡片圆角、图片比例和媒体失败占位规则。

首页需在 Pixel 8 主尺寸以及 360px、412px、140% 字体下验证，无溢出、遮挡或底栏覆盖。

## 7. P3：重点足球页面与淘汰树入口

页面顺序为：数据中心 → 比赛详情 → 球队详情 → 球员详情。

重点要求：

- 数据中心的赛事、赛季、赛程、积分榜和排名层级清楚；
- 比赛详情的总览、资讯、统计、阵容和评分均使用真实 API 数据；
- 阵容按阵型呈现 11 名首发，头像可复用但姓名、位置和队伍必须正确；
- 球队和球员详情中的头像、动态、数据、赛程与 P1 数据保持一致；
- 杯赛页面增加可发现的“淘汰树/总览”入口；
- 占位页明确显示“淘汰树正在开发”，可正常返回，不展示伪造对阵数据，并保留后续接入真实接口的稳定路由。

## 8. P4：剩余页面与整体收口

在重点页面通过后，再按以下顺序处理：

1. 内容详情、评论、发布和搜索；
2. 用户主页、关系、通知和设置；
3. 首次选择和现有账号登录结构；
4. 全部纳入原型的截图复验与回归。

手机号登录扩展和通信能力继续保持排除状态，不进入本阶段。

## 9. 统一验收标准

单个页面只有同时满足以下条件才算完成：

- 主要结构、模块顺序、视觉重心和信息密度接近对应原型；
- 使用真实 API，不在生产 Widget 中硬编码业务数据；
- 图片可见，长短文案、缺图、空列表和失败状态能自然降级；
- 路由、返回、滚动、分页及已有点赞/收藏/评论/关注/评分/发布交互不回归；
- 定向测试与 `flutter analyze` 通过；
- 有当前代码生成的设备截图，并完成人工视觉确认。

最终收口时，所有原型都必须标记为“已完成、本轮排除、后续专项”之一；自动测试通过不能替代人工截图验收。

## 10. 后续分计划顺序

本轮不生成分计划。总计划确认后，仅按以下五个小批次依次制定：

1. 图片与内容封面修复；
2. 旗舰比赛及关键演示数据补齐；
3. 首页推荐、资讯和比赛排布；
4. 数据中心、足球详情和淘汰树占位入口；
5. 剩余页面与整体验收。

每个分计划只描述一个可验收批次，必须写清允许修改范围、保护项、最小验证、截图要求和完成条件，不提前夹带下一阶段工作。

## 11. 本轮完成定义

本轮项目完成需同时满足：

- 关键图片与封面在客户端可见；
- 旗舰比赛能完整呈现阵容等重点原型内容；
- 首页推荐、资讯和比赛排布通过人工视觉验收；
- 数据中心和足球详情页使用真实数据并接近原型；
- 杯赛淘汰树入口及“正在开发”占位可用；
- 排除能力未被伪实现；
- 数据变更幂等、可回滚且未破坏非 DEMO 数据；
- 完整淘汰树后端能力已登记为下一阶段独立必做专项。
