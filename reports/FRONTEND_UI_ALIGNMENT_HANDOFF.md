## 6. 当前核心问题

自动测试通过主要说明行为正确和没有明显布局异常，不能证明截图级还原。当前人工反馈是多个页面与原型仍有差距，接手模型必须重新建立最新截图基线。

重点风险：

| 风险 | 表现 |
| --- | --- |
| 默认 Material 感仍然明显 | AppBar、Card、ListTile、Dropdown、Tab 的默认尺寸可能与原型不一致 |
| 页面之间缺少统一尺度 | 相似标题、按钮、头像、圆角和间距可能来自不同实现轮次 |
| 局部组件通过、整页构图不一致 | 单卡片尺寸正确，但和头部、筛选区、底栏组合后比例失衡 |
| 测试代替了视觉对照 | 过去很多验收只看 Key、状态或无 overflow，没有最新截图证据 |
| 数据长度影响观感 | 真实或本地数据的标题、图片和数量与原型不同，需要验证弹性布局 |

## 8. 每轮执行方法

### 第一步：建立可复现截图

在 Android 模拟器运行当前代码：

```powershell
cd D:\Football-APP-Front\apps\mobile

flutter run -d emulator-5554 `
  --dart-define=APP_ENV=development `
  --dart-define=API_BASE_URL=http://10.0.2.2:8080
```

如果设备 ID 变化，先运行 `flutter devices`，不要写死不存在的设备。需要本地 API 时，先确认对应服务已启动；如果本轮只做可控 mock 页面，应沿用已有测试注入方式，不把 mock 写进生产 Widget。

### 第二步：建立对照表

每个页面至少记录：

| 字段 | 内容 |
| --- | --- |
| 原型文件 | 例如 `首页.png` |
| 当前截图 | 使用当前提交实际运行生成 |
| 屏幕参数 | 设备、逻辑宽度、DPR、系统字体比例 |
| 结构差异 | 模块顺序、头部高度、卡片组合、底栏位置 |
| 样式差异 | 色值、字号、行高、间距、圆角、阴影、图标 |
| 数据差异 | 只记录对布局的影响，不复制原型示例数据 |
| 修复文件 | 实际改动文件 |
| 复验结果 | 新截图、自动测试和人工结论 |

建议将新证据放在新目录，例如 `reports/prototype-alignment-current/`，不要覆盖旧 F18 截图。

### 第三步：先修公共差异

同一差异出现在三个以上页面时，优先检查：

- `apps/mobile/lib/shared/design_system/`
- `apps/mobile/lib/app/theme/app_theme.dart`
- `apps/mobile/lib/shared/widgets/`
- 页面族自己的公共 widgets

公共修改必须向后兼容；如果会改变大量页面，应先挑 2–3 个代表页面验证，不要直接全局替换。

### 第四步：页面级修复

- 保持现有 controller/repository/router；
- 优先调整页面组合、布局和可选视觉参数；
- 不把固定高度用于超长原型页面；
- 不以截图作背景；
- 不删除 loading/empty/error/retry/403/unknown 状态；
- 保留稳定 Key、曝光/推荐归因和点击链路。

### 第五步：双重验收

每轮必须同时满足：

1. 自动验证：`flutter analyze`、本页面族定向测试、`git diff --check`；
2. 视觉验证：原型与最新运行截图并排比较，人工确认主要差异已关闭。

仅自动测试通过不得标记“原型对齐通过”。

## 9. 完成标准

单个页面只有同时满足以下条件才可标记完成：

- 页面结构和内容顺序与原型一致；
- 头部、主体、底栏的比例接近原型；
- 字体、颜色、圆角、阴影、间距和图标体系一致；
- 本地数据长短变化时仍可用，不为示例数据定制；
- 360px、412px、100% 和 140% 字体无溢出或遮挡；
- loading、empty、error、retry、nullable、unknown 和媒体失败仍正常；
- 路由、返回状态、分页和业务操作没有回归；
- 有当前提交生成的截图证据和对应定向测试结果。

整项前端只有在 60 张原型的“实现/排除/需产品决策”状态都明确，并完成主链路人工复验后，才可以称为最终完成。
