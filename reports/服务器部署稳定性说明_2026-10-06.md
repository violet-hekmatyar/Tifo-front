# 南看台 App 云服务器部署稳定性说明

> 面向对象：非技术同事与项目决策者
> 报告日期：2026-10-06
> 结论先行：**软件本身部署正确、可以运行，但这台服务器配置太小，扛不住，会反复"死机"。需要升级服务器配置才能稳定使用。**

---

## 一、一句话说清问题

我们要在这台服务器上同时跑 **三个软件**（数据库、缓存、后端程序），但服务器的内存只够跑 **两个半**。

就像一张只能坐 5 个人的桌子，硬要坐 7 个人——刚开始能挤下，一旦有人动作大一点（数据变多、有人访问），整张桌子就翻了。

---

## 二、这台服务器有什么

| 项目 | 实际情况 |
|---|---|
| 服务商 | 阿里云（广州） |
| 系统 | Ubuntu 24.04 |
| **内存** | **894 MB**（不足 1 GB） |
| CPU | 2 核 |
| 硬盘 | 30 GB（剩 20 GB，够用） |
| 实例 ID | `i-7xv7q1nhlkeouqka6pv2` |

**内存是唯一的瓶颈。** 硬盘和 CPU 都够。

---

## 三、这台上要跑什么（内存开销明细）

| 软件 | 作用 | 占用内存 |
|---|---|---|
| 操作系统本身 | 维持系统运转 | 约 120 MB |
| Docker 容器引擎 | 用来隔离运行数据库 | 约 125 MB |
| 阿里云安全/监控插件 | 云平台自带，不可移除 | 约 46 MB |
| MySQL 数据库 | 存所有业务数据 | 约 150 MB |
| Redis 缓存 | 加速访问 | 约 6 MB |
| **Spring Boot 后端程序** | **我们开发的业务程序** | **需要 300~500 MB** |
| **合计** | | **约 750~950 MB** |

**服务器可用内存 894 MB，需求 750~950 MB。**
平时勉强够用，一旦程序内存涨一点，就会超出——超出后系统的应对方式是**强制杀掉一个程序**，而它杀谁是不确定的。

---

## 四、已经真实发生过两次故障

### 故障一：2026-07-04（上一轮部署期间）

系统日志（`dmesg`）明确记录：

```
2026-07-04 11:54:07  Out of memory: Killed process 549465 (java)
```

翻译：**系统内存不足，强制杀掉了后端程序。**

同一次事故还连带杀掉了系统管理进程，说明整机已经失控。这之后后端就一直没有再运行。

### 故障二：2026-10-06（本次部署）

本次把后端程序、数据库都更新到最新版本后，服务器**直接卡死**：

| 检查项 | 结果 | 说明 |
|---|---|---|
| 网络能否连通 | ✅ 通（延迟 4 毫秒） | 服务器没断电 |
| 22 端口能否握手 | ✅ 能 | 服务器仍在运行 |
| SSH 能否登录 | ❌ **完全无响应** | 系统已无法响应用户操作 |
| 网站服务能否访问 | ❌ 无响应 | 业务不可用 |

**状态是：机器开着，但什么也做不了。**

### 故障三：2026-10-06 晚 —— 对照实验（最有力的证据）

为确认"到底是不是后端程序撑爆了服务器"，我们做了一次对照实验：**把后端程序停掉，观察服务器；再启动它，观察服务器。**

| 时刻 | 后端状态 | 系统负载 | 可用内存 |
|---|---|---|---|
| 22:25:29 | 刚停止 | **19.39** | 297 MB |
| 22:26:53 | 停止中 | 4.87 | — |
| 22:28:18 | 已停止 3 分钟 | **1.47** | 289 MB |
| 22:28:41 | **重新启动** | 1.98 | 95 MB |
| 22:29:06 | 启动 50 秒 | **14.24** | **91 MB** |

**结论非常清楚：**

- 后端**一停**，负载从 19.39 掉到 1.47（正常水平）
- 后端**一起**，可用内存立刻从 289 MB 掉到 91 MB，负载窜到 14.24，SSH 随即失联

**拖垮服务器的就是后端程序本身，不是网络问题、不是别人攻击、也不是数据量太大。**

（补充：当时数据库最大的表只有约 1 万行，数据量极小。所以这不是"数据太多"，而是"内存总量不够装下这些程序"。）

### 故障四：2026-10-06 深夜 —— 容量极限实测（最关键的结论）

在把内存参数压到极限之后，服务器**闲置时已经稳定**（负载 0.09）。于是我们做了一次真实访问测试：

**测试方式：模拟 6 个用户同时打开 App 首页，共请求 60 次。**

| 测试结果 | 数值 |
|---|---|
| 成功返回 | **仅 15 次（25%）** |
| 失败/超时 | **45 次（75%）** |
| 最快响应 | 1.1 秒 |
| 平均响应 | **23.4 秒** |
| 最慢响应 | **30.2 秒（超时）** |
| 测试后系统负载 | **34.00**（2 核机器，超载 17 倍） |

**结论：**

- **闲置时**：服务器正常
- **只要 6 个人同时打开首页**：四分之三的请求失败，平均要等 23 秒，服务器再次卡死

**这就是这块硬件的真实容量上限——连一场小规模演示都撑不住。**

## 五、为什么"数据变多"会让情况更糟

本次部署过程中发现：服务器上的数据库是 **7 月初初始化的**，而程序是 **9 月底的新版本**，两者已经对不上：

| | 表数量 | 足球数据量 |
|---|---|---|
| 服务器原有数据库（7月） | 18 张表 | 极少（示例数据） |
| 现在程序需要 | **36 张表** | 8 联赛 / 192 球队 / **4182 球员** / 1403 场比赛 |

**后果一：功能报错。** App 首页（信息流）直接返回"系统异常"。原因就是程序要查的表在服务器数据库里根本不存在。

**后果二：内存吃紧。** 我们已经把正确的数据（完整 36 张表、全部真实足球数据）导入服务器并校验两边数据量完全一致。数据变多之后，数据库和程序的内存占用都上升，把原本就紧张的内存彻底压垮。

---

## 六、这算不算"部署失败"？

**要分两面看：**

✅ **部署本身是成功的**——我们验证过：
- 后端程序正常启动、健康检查通过
- 数据库结构已更新到最新（36 张表）
- 数据已完整导入，与开发机完全一致
- 已配置为"开机自启 + 崩溃自动重启"
- 发现并修复了首页报错的根本原因（数据库版本落后 3 个月）

❌ **但以"能稳定给人用"为标准，目前是失败的**——服务器现在卡死，且在原配置下会反复卡死。

**结论：这不是软件没做好，而是"小马拉大车"。** 把同一个程序放到配置足够的服务器上，就能正常跑。

---

## 七、解决方案（三选一）

### 方案一：升级服务器配置（推荐）

把内存从 894 MB 升到 **4 GB**。

- **优点**：彻底解决问题，配置足够后稳定性有保障；阿里云支持在线变更配置，不用重新部署
- **缺点**：产生额外费用（具体金额请以阿里云控制台实际报价为准）
- **工作量**：小，配置变更后原部署可直接复用

### 方案二：改用阿里云托管数据库

把 MySQL 和 Redis 从这台服务器挪到阿里云的托管服务（RDS / Redis 版）。

- **优点**：能省出约 280 MB 内存，后端程序单独跑会稳一些
- **缺点**：仍有约 600 MB 需求压在 894 MB 上，只能算缓解；且托管数据库本身也要付费，成本可能高于方案一

### 方案三：保持现状，仅调优

把各软件的内存参数压到极限，把能关的系统服务关掉。

- **优点**：不花钱
- **缺点**：**只是缓解，不能根治**。程序只要稍微忙一点就会再次卡死。**不建议用于任何正式或演示场景**

| 优先级 | 事项 |
|---|---|

**在完成第 1 项之前，不建议安排任何对外演示或用户试用。**

## 附录二：升级内存后的恢复步骤

内存升级 + 重启实例完成后，只需执行以下两条命令即可恢复服务（全部已配置好，无需重新部署）：

```bash
# 1. 恢复开机自启并启动后端
systemctl enable --now south-stand.service

# 2. 验证（约 30 秒后）
curl http://127.0.0.1:8080/api/public/health
# 期望返回 {"code":0,...,"status":"UP"}
```

如果升级到 4 GB，建议同时放宽当前为极限压缩而设的内存限制（当前值过紧）：

```bash
# /etc/systemd/system/south-stand.service
#   JAVA_OPTS  的 -Xmx192m  ->  -Xmx1g
#   MemoryHigh 250M         ->  1200M
#   MemoryMax  320M         ->  1500M
# 然后：
#   /opt/south-stand/docker-compose.yml 的 innodb-buffer-pool-size 48M -> 512M
systemctl daemon-reload && systemctl restart south-stand.service
```

**已完成、无需重做的部分：**

- 后端 jar 已部署（`/opt/south-stand/backend/south-stand-server.jar`，SHA-256 `de23051c…a6ce7`）

  - 后端地址 `http://8.138.118.219:8080` 已烧入
