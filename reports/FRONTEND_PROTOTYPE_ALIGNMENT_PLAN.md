# 足球 APP 前端原型对齐计划

## 1. 计划目标

本计划用于将现有 Flutter 客户端逐步对齐 `C:\Users\hekmatyar\Desktop\足球APP` 中新增的 60 张原型图。

当前阶段的数据仍使用本地模拟数据。后续开发以前端视觉、布局、交互和页面状态为主，保留清晰的数据访问边界，模拟数据集中放在现有数据层或专用 mock 层，不把固定数据直接写进页面组件。待界面对齐稳定后，再单独规划真实后端联调。

手机号验证码登录和微信登录暂不实现。登录模块只保留当前可运行的登录方式及必要视觉调整，不制作无法真实完成的入口和伪交互。

原型图只作为产品和视觉参考，其中出现的示例文案、球队、球员、比分和消息不直接写成生产数据。

## 3. 总体视觉方向

现有客户端主要采用紫色 Material 风格；新原型形成了更明确的足球社区视觉体系：

| 区域 | 原型表现 | 建议实现方式 |
| --- | --- | --- |
| 全局品牌色 | 内容社区以绿色为主 | 建立新的语义色 Token，不在页面中散落颜色常量 |
| 球队/球员详情 | 酒红色沉浸式头部 | 使用可配置的详情头部组件，不复制多个相似页面 |
| 比赛详情 | 深色球场氛围头部 | 独立比赛上下文主题，正文仍复用全局卡片和文字规范 |
| 页面背景 | 浅灰底、白色圆角内容块 | 统一页面容器、卡片圆角、间距、阴影和分割线 |
| 底部导航 | 悬浮胶囊式导航 | 替换当前标准 Material NavigationBar，保留现有导航状态 |
| 列表与榜单 | 信息密度较高、层级更清晰 | 建立统一表头、排行行、筛选器和分页/到底状态 |
| 弹层 | 圆角底部弹层为主 | 统一分享、筛选、协议和选择器弹层 |

正式开发前需要从原型源文件或产品确认稿中确定准确色值、字体等级和间距。截图颜色只用于判断方向，不建议直接肉眼取值后当作最终规范。

## 5. 前端实施原则

1. 保留当前数据层、Repository、Controller 和路由边界，优先替换表现层；当前使用本地模拟数据，不因视觉改版把数据硬编码进 Widget。
2. 先建立公共视觉基础，再改业务页面，避免同一种卡片、筛选器和空态在不同页面重复实现。
3. 页面必须覆盖 loading、empty、error、retry、无权限、字段为空和 unknown 类型；本地模拟数据用于验证这些状态，但原型截图中的示例不能直接散落在生产 Widget 中。
4. 保留当前已完成的路由返回状态、分页去重、登录态判断、关注关系、推荐 attribution 和行为上报。
5. 手机号登录和微信登录明确暂缓；私信、复杂杯赛树等大功能也不包装成简单 UI 调整，确认范围后另立任务。
6. 每完成一个模块即做定向验证和截图比对，不等所有页面改完才处理公共布局问题。

## 7. 分阶段执行计划

### 阶段 A：视觉基础与主框架

**前端工作**

- 固化颜色、字体、间距、圆角、阴影、图标尺寸和状态色。
- 建立绿色全局主题及球队/球员、比赛等上下文主题。
- 改造主框架顶部区域、页面背景和悬浮底部导航。
- 统一 SafeArea、键盘避让、状态栏颜色和不同屏幕宽度表现。

**完成判断**

- 四个主入口切换和状态保持不回归。
- 公共组件在常规字体和较大系统字体下无溢出。
- 后续页面不再直接依赖旧紫色视觉常量。

### 阶段 B：首页与 Feed（最高优先级）

**前端工作**

- 对齐搜索、发布、推荐/资讯/关注 Tab 和球队/联赛快捷筛选。
- 将 CONTENT 卡片调整为双列瀑布流；MATCH、HOT_COMMENT、DISCUSSION、RANKING、PLAYER_RATING 按原型使用全宽卡片。
- 复用现有 Feed 模型和 attribution；各卡片的本地模拟数据集中维护，不写进 Widget。
- 保留 unknown cardType 安全降级。
- 完善刷新、分页、空态、错误重试和返回后的滚动位置。
- 按已确认交互：用户向下浏览时，返回顶部按钮渐进出现；用户向上滚动时渐进消失，点击后平滑回到顶部。

**完成判断**

- 六类卡片均能在定向模拟数据下正确渲染。
- 双列与全宽卡片混排不重叠、不截断。
- 切换频道、球队和分页时无旧请求污染。

### 阶段 C：内容、搜索、发布与评论

**前端工作**

- 对齐帖子/文章详情的排版、作者区、关系内容和底部互动栏。
- 对齐帖子/文章编辑状态、封面、正文、关联实体选择和发布反馈。
- 实现分享底部弹层并对接系统分享能力。
- 对齐评论列表、楼中楼摘要、回复对象、输入状态和删除/失败反馈。
- 调整全局搜索的搜索框、分类、结果项、历史/空态；空关键词不请求。

**后续数据能力判断点**

- TEAM/PLAYER/MATCH 关联和四类搜索当前使用本地模拟数据，并继续遵守既有模型结构。
- 如果话题和热门事件必须成为可维护、可搜索并可关联的真实实体，留到后端联调阶段定义契约；当前只允许以明确的 mock 数据源验证界面。

**完成判断**

- 发布、详情、互动、搜索和返回状态形成完整闭环。
- 403、删除内容、空评论和上传失败有明确状态。

### 阶段 D：数据中心与榜单

**前端工作**

- 重做赛事、赛季、阶段和指标筛选区，解决当前控件拥挤或调试标记污染问题。
- 对齐赛程、积分榜、球员榜、球队榜和重点比赛卡片。
- 统一排行行、升降级/晋级标识、球队与球员跳转。
- 长榜单保持流畅分页或分段加载，不在客户端伪造排名。

**后续数据能力判断点**

- 常规联赛/赛季榜单当前先用本地模拟数据完成界面和状态验证。
- 欧冠复杂淘汰树不是现有小幅后端修改；本期可先用符合现有模型的模拟数据展示阶段/比赛列表，完整树形能力另立专项。

**完成判断**

- 联赛、赛季、阶段、指标切换准确清理旧数据。
- 表格在窄屏、长队名和大字体下可读且不出现布局污染。

### 阶段 E：球队、球员与比赛详情

**球队详情**

- 对齐酒红色头部、队徽、关注/主队、球队价值和五类核心 Tab。
- 组合下一场比赛、当前排名、内容、射手/助攻、基础资料和荣誉模块。
- 阵容按位置展示，赛程、内容、统计使用模拟分页验证加载、到底和空态。

**球员详情**

- 对齐球员头部、当前俱乐部、可空国家队、退役状态和历史球队。
- 对齐生涯时间轴、统计、比赛、内容和荣誉陈列。
- 能力雷达只在后端提供明确、可解释的多维真实数据时显示；否则使用合适空态，不自行推导。

**比赛详情**

- 对齐深色球场头部、比赛状态、比分、评分、总览、阵容、排行和统计 Tab。
- 重做比赛事件时间线、技术统计对比条和阵型球场布局。
- 视频集锦、裁判评分等缺少正式能力的区域不伪造。

**完成判断**

- 球队、球员、比赛、内容之间的现有互相跳转不回归。
- 所有可空字段和退役/未开赛/已结束等状态均能自然降级。

### 阶段 F：用户中心、登录引导、通知与设置

**前端工作**

- 对齐本人/公开用户头部、统计、关注关系和内容 Tab。
- 对齐发布、点赞、收藏、评论、关注/粉丝列表。
- 对齐通知列表、未读状态、头像和统一空态。
- 对齐绿色登录页、协议弹层、错误状态和首次关注引导。
- 设置页先展示已有可执行功能；没有真实闭环的入口不得伪装成可用。

**后续能力判断点**

- 互动通知已有接口，可直接改前端。
- 原型中的用户会话/私信属于完整 IM 能力，不是小幅补充；建议保留为后续独立功能，不在本轮制造假会话。
- 手机验证码、微信登录明确暂不实现；本轮保留当前可运行登录方式，只对齐兼容的视觉结构。
- 修改手机号、密码、安全验证等设置入口，需要逐项确认后端真实接口后再开放。

**完成判断**

- SELF/NONE/FOLLOWING/FOLLOWED_BY/MUTUAL 显示和操作准确。
- 登录态、未登录态、隐私 403 与真实空列表视觉上可区分。

### 阶段 G：整体验收与收口

**验证范围**

- 按原型逐页建立“原型—实现”截图对照，不只检查单个控件。
- 覆盖主链路：登录/引导 → 首页 → 搜索/发布 → 内容互动 → 数据榜单 → 球队/球员/比赛详情 → 用户中心。
- 检查 loading、empty、error、retry、403、离线、慢请求、图片失败和 unknown 数据。
- 检查常用 Android 尺寸、系统大字体、中文/英文长文本、键盘和安全区。
- 定向运行相关测试、`flutter analyze`，最后再进行必要的真机/模拟器人工验收。

**完成判断**

- 页面视觉结构、内容顺序、交互反馈与原型一致。
- 不存在生产 mock、占位数据、调试标记或布局溢出。
- 已有页面跳转、交互和状态流转不因视觉改造退化。

## 8. 后端改动分级

| 分级 | 内容 | 本轮建议 |
| --- | --- | --- |
| 当前无需改后端 | 首页六类 Feed、文章/帖子、评论、搜索、榜单、球队/球员/比赛详情、关注、用户内容、互动通知 | 先用集中管理的本地模拟数据完成界面对齐 |
| 可评估的小范围补充 | 话题/热门事件实体和关联；少量设置项；原型展示但现有模型确实缺少的单个可维护字段 | 必须先确认真实业务和接口契约，再单独实现、测试和迁移 |
| 不属于小幅修改 | 私信/IM、手机号验证码、微信登录、复杂杯赛淘汰树、实时比分推送、完整视频中心、复杂热图/传球图 | 不纳入本轮视觉对齐，另立后续专项 |

后端若需调整，应继续遵守现有 Result/PageResult、枚举、nullable、分页和权限约定；不能为还原截图而返回固定 Demo 数据。

## 9. 工作量侧重点

| 工作类型 | 预计占比 | 说明 |
| --- | ---: | --- |
| 页面布局与视觉组件 | 高 | 现有紫色 Material 风格与原型差异明显，是主要工作量 |
| 交互与页面状态 | 高 | 瀑布流混排、筛选、弹层、评论、详情长页、滚动状态较多 |
| 现有数据适配 | 中 | 重点是用本地模拟数据覆盖 nullable、分页、空态和错误态，并保持未来接口映射边界 |
| 路由与状态保持 | 中低 | 基础已具备，主要防止改版回归 |
| 后端补充 | 低且受控 | 只处理确认后的独立小缺口，不扩展为大型新业务 |

建议实施顺序为：**视觉基础 → 首页 Feed → 内容/搜索/发布 → 数据榜单 → 三类详情 → 用户/登录/通知 → 整体验收**。这样可以先交付用户最容易感知的界面变化，同时让后续页面持续复用前面沉淀的组件。

| 决策 | 推荐默认方案 | 原因 |
| --- | --- | --- |
| 精确视觉规范 | 从可用的原型源文件/设计标注确认；暂无标注时建立一次统一取值 | 避免不同页面各自猜色和猜间距 |
| 手机号与微信登录 | 明确暂不实现；不显示伪可用入口 | 新登录方式需要第三方服务和账号安全设计 |
| 消息页面 | 本轮只对齐互动通知界面，私信另立专项 | 当前后端没有 IM 契约 |
| 欧冠淘汰树 | 本轮使用现有模型的模拟阶段/比赛，完整树另立专项 | 复杂杯赛树不是表现层小改 |
| 话题/热门事件 | 若确认为必需，先定义最小实体、查询和关联契约 | 避免把截图中的示例选择项硬编码到生产环境 |
| 能力雷达、视频等数据 | 有真实数据才显示，无数据使用明确空态 | 不从其他统计主观推导或伪造 |

以上默认方案可以保证先完成主要前端视觉改版，并让本地模拟数据与未来真实接口保持清晰边界。

## 11. 分轮推进与验收机制

本计划由计划/验收模型维护，具体代码由另一执行模型逐轮完成。每一轮只处理一个页面族或一个公共能力，不并行扩张到下一轮。

### 固定工作流

1. 计划模型给出并保存本轮 Prompt，明确原型参考、修改范围、禁止事项、最小验证和带编号的验收矩阵。
2. 每轮保持一个完整业务域，但在 Prompt 内拆成 3–5 个顺序执行阶段；执行模型必须完成一个阶段的代码与定向测试后再进入下一阶段。
3. 执行模型只执行当前 Prompt，不顺带重构其他页面，不提前实施下一轮；不得因首个测试失败或发现一个问题就提前结束。
4. 最终汇报必须逐项列出“验收编号—实现文件—测试名称—结果”；没有代码或测试证据的项目不得标记完成。
5. 计划模型检查实际 diff、测试名称和验收矩阵，不只接受文字总结。未完成项继续留在原轮次，不用“现有逻辑保留”“后续可补”代替实现。
6. 只有缺少契约、必要权限、外部服务或会导致越权/破坏性修改时才算阻塞；普通编译错误、测试失败和布局问题属于本轮应继续修复的工作。
7. 若发现问题，先给出同轮修复 Prompt；当前轮全部强制项通过后，才生成下一轮 Prompt。
8. 共性设计一旦通过验收，后续轮次必须复用，避免每个页面独立造样式。

### 执行模型完成率约束

后续 Prompt 统一采用以下规则：

- **先核对再实现**：只读取允许范围内的现有入口、状态和测试，建立内部清单，不输出长篇计划。
- **按阶段闭环**：每阶段同时包含生产实现和对应测试，禁止先堆全部 UI、最后才发现行为不可测。
- **失败继续处理**：首次失败用于定位根因；只要问题仍在范围内，就修复并重跑，不把普通失败报告为阻塞。
- **证据式交付**：每个强制要求至少对应一个可定位的实现点或行为级测试；视觉项至少有窄屏/大字体覆盖。
- **成功标志受控**：只有静态分析、指定测试和全部验收编号通过时才能输出成功标志；部分完成必须明确缺失编号。
- **任务量控制**：轮次可以覆盖一个完整页面族，但不同时横跨两个独立业务域。任务量通过纵向闭环增加，而不是横向扩散。
