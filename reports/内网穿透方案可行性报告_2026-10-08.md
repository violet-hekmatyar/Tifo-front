# 内网穿透方案可行性报告

> 调研日期：2026-10-08
> 场景：用户量 < 10 人的测试阶段
> **结论：可行，推荐采用。但必须先修一个已确认的安全漏洞（见第三节）——修之前不要让公网访问。**

---

## 一、方案结论

**把后端跑在你的本机，用阿里云服务器做「中转站」，让手机通过公网访问本机后端。**

| | 原方案（后端跑阿里云） | 新方案（本机 + 穿透） |
|---|---|---|
| 算力 | 2 核 / 894 MB → **跑不动** | **24 核 / 31.7 GB → 绰绰有余** |
| 阿里云角色 | 承担全部计算 | **只做流量转发（几乎不耗资源）** |
| 内存问题 | 差 150~200 MB，无解 | **彻底消失** |
| 成本 | 需升级到 4 GB | **不花钱**（复用现有服务器） |
| 域名/备案 | 不需要 | **不需要** |
| 6 并发用户 | **75% 请求失败** | **10/10 全部成功**（已实测） |

**核心逻辑：** 你的本机比阿里云服务器强 **35 倍**（内存）。原来阿里云既是计算中心又是流量入口，所以被压垮；现在让它只当"门卫"，计算全部回本机——瓶颈从"算力不够"变成"上行带宽够不够"，而实测证明 10 人以内完全够。

## 二、实测数据（全部为真机实测，非估算）

### 2.1 硬件对比

| | 阿里云 ECS | 你的本机 |
|---|---|---|
| CPU | 2 vCPU | **Intel i7-13700 / 24 逻辑核** |
| 内存 | 894 MB | **31.7 GB** |
| 后端状态 | 已停（跑不动） | **正在运行，健康检查 UP** |

### 2.2 网络带宽

| 方向 | 实测 | 说明 |
|---|---|---|
| 阿里云 → 本机 | **25.86 Mbps** | 阿里云出口带宽充足（**远好于担心的 1 Mbps**） |
| 本机 → 阿里云（持续） | **11.69 Mbps（1.46 MB/s）** | 家庭宽带上行，**这是真正的瓶颈** |

> 注：单张图片瞬时可达 2.6~5.0 MB/s，但持续性吞吐稳定在 1.46 MB/s。容量规划要按 **1.46 MB/s** 算。

### 2.3 隧道连通性验证（已实测通过）

在阿里云服务器上通过反向隧道访问本机后端，**全部正常**：

| 接口 | 结果 |
|---|---|
| `GET /api/public/health` | ✅ `{"code":0,...,"status":"UP"}` |
| `GET /api/app/feed?tab=recommend` | ✅ 返回真实比赛卡 |
| `POST /api/auth/login` | ✅ 返回有效 Token |

### 2.4 隧道性能

| 测试项 | 实测结果 |
|---|---|
| API 延迟（首页 Feed） | **0.12 ~ 0.15 秒** |

| **10 个并发请求首页** | **10/10 全部成功（200）**，总耗时 **0.2 秒**，平均 133 ms |

**对比原方案：同样是「用户访问首页」，阿里云自跑后端时 6 并发就 75% 失败；穿透方案 10 并发全部成功。**

## 三、必须先修的安全漏洞（已实测确认，非理论风险）

### 问题

本机后端当前是用这条命令启动的，**没有设置任何环境变量**：

```
java -jar target/south-stand-server.jar --server.port=8080
```

而配置 `application.yml:59` 中 JWT 密钥的默认值是硬编码的开发占位串：

```yaml
secret: ${JWT_SECRET:dev_only_change_me_jwt_secret_please_override_in_prod_2026}
```

### 验证过程与结果

我用这个**公开可见的默认密钥**伪造了一个 `roleType=ADMIN` 的令牌，调用 `/api/auth/me`：

```
用伪造令牌访问 /api/auth/me 的结果:
  {"code":0,"message":"success","data":{"id":10001,"username":"admin",
   "nickname":"South Stand Editorial","roleType":"ADMIN","status":"ACTIVE",...}}
```

**后端接受了伪造令牌，并返回了管理员身份数据。**

### 影响

**当前状态下，任何人只要知道这个密钥（它明写在代码配置里），就能冒充管理员，任意调用管理员接口、读写全部用户数据。**

在内网跑没问题；**一旦通过穿透暴露到公网，就等于把系统完全开放。**

### 修复（必须先做）

启动时设置一个足够长、随机、不公开的密钥：

```powershell
$env:JWT_SECRET = "<随机生成的长字符串，至少64字符>"
java -jar target/south-stand-server.jar --server.port=8080
```

生成随机密钥：

```powershell
[Convert]::ToBase64String((1..64 | ForEach-Object { Get-Random -Max 256 }))
```

**同时建议：** 目前跑的是 `dev` 配置（逐条打印 SQL 日志），公网暴露前建议改为生产配置，减少日志量并避免敏感信息落到日志里。

## 四、推荐架构

```
手机 App（已构建好的 APK）
   │  http://8.138.118.219:8080
   ▼
阿里云 ECS  8.138.118.219   ← 只做转发，几乎不耗资源
   │
   ▼  出站长连接（穿透 CGNAT，无需公网 IP）
   你的本机  i7-13700 / 31.7 GB
   ├── Spring Boot 后端  :8080   ← 承担全部计算
   ├── MySQL            :3306   ← 仅监听 127.0.0.1
   └── Redis            :6379   ← 仅监听 127.0.0.1
```

### 4.1 两种穿透实现（二选一）

**方案 A：SSH 反向隧道（零额外软件，本次已用它验证成功）**

```powershell
ssh -N -R 8080:127.0.0.1:8080 root@8.138.118.219
```

- 优点：不需要装任何东西，复用已开放的 22 端口，**立即能用**
- 缺点：需要在服务器 `sshd_config` 里开启 `GatewayPorts clientspecified`（否则只能绑到服务器本机，外部访问不到）；断线需重连（用 `autossh` 或计划任务守护）

**方案 B：frp（推荐，更稳更专业）**

阿里云 `/opt/frp/frps.toml`：

```toml
bindPort = 7000
auth.method = "token"
auth.token = "<换成强随机串>"
allowPorts = [{ single = 8080 }]
```

本机 `C:\frp\frpc.toml`：

```toml
serverAddr = "8.138.118.219"
serverPort = 7000
auth.method = "token"
auth.token = "<与上面一致>"

[[proxies]]
name = "south-stand-api"
type = "tcp"
localIP = "127.0.0.1"
localPort = 8080
remotePort = 8080
transport.useCompression = true
```

- 优点：专为穿透设计，自带断线重连、状态面板，长期更省心
- 缺点：需额外开放 **7000** 端口

### 4.2 阿里云安全组需要放行

| 方向 | 端口 | 用途 |
|---|---|---|
| 入方向 | **8080** | 手机访问后端（**两种方案都必须**） |
| 入方向 | 7000 | 仅方案 B（frp）需要 |
| 入方向 | 22 | 你的管理 IP |

**仍然不要开放 3306 / 6379。**

### 4.3 APK 无需重新构建

已构建的 Release APK 指向 `http://8.138.118.219:8080`，并且明文 HTTP 白名单已放行该 IP——**这个架构直接复用同一个 APK，不用重新打包。**

## 五、带宽容量分析（< 10 人）

### 5.1 好消息：大部分图片不走隧道

实测数据库中的图片地址分布：

| 图片来源 | 数量 | 是否走隧道 |
|---|---|---|
| 球队队徽 `football_team.logo_url` | **192 / 192 全部外链** | ❌ 不走（来自 football-data.org） |
| 球员头像 `football_player.avatar_url` | 2937 外链 + 108 本地 | 绝大部分不走 |
| 内容封面 `content.cover_url` | 210 个 `/demo/p1-media/*` | ✅ 走隧道 |
| 内容媒体 `content_media.media_url` | 145 个本地 | ✅ 走隧道 |

**结论：队徽、绝大多数头像都是外链，完全不经过隧道和你的家庭宽带。** 走隧道的只有内容封面类图片，共 72 个文件、总计 8.8 MB（打包在 jar 里）。

### 5.2 容量测算

| 场景 | 测算 |
|---|---|
| 首页 API 请求 | 约 50~100 KB/次 → 10 人并发毫无压力（已实测 10/10 成功） |
| 首次加载全部封面图 | 8.8 MB ÷ 1.46 MB/s ≈ **6 秒**（10 人同时首次打开） |
| 二次访问 | 图片已在手机本地缓存，**几乎不占带宽** |

**判断：< 10 人测试阶段完全够用。** 首次打开 App 时图片会稍慢（秒级），之后流畅。

### 5.3 可选优化（若觉得首次加载慢）

在阿里云上放一个 Nginx，对隧道端口做**反向代理 + 缓存**。图片第一次被访问后缓存在阿里云，之后所有用户都从阿里云以 25+ Mbps 的速度拿，不再占用家庭宽带上行。

**但 10 人以内存疑是否需要**——建议先跑起来看实际体验，不够再加。

## 六、运维注意事项

| 项目 | 说明 |
|---|---|
| **本机必须常开** | 关机/断网/休眠 = App 不可用。建议关闭自动休眠、设置断电恢复后自动开机 |
| **穿透客户端自启** | frpc 可用 WinSW 注册为 Windows 服务；SSH 方案用 `autossh` 或计划任务 |
| **数据库安全** | 本机 MySQL/Redis 已只监听 127.0.0.1 ✅，不要改为 0.0.0.0 |
| **本机其他服务** | 本机还跑着 nginx(80)、nacos、milvus 等，**只穿透 8080 一个端口**，其余保持私有 |
| **延迟** | 手机 → 阿里云广州 → 本机，实测 API 延迟 0.12~0.15 秒，体验良好 |
| **IP 变动** | 家庭宽带动态 IP 无影响（穿透是主动出站连接）；CGNAT 无影响 |

## 七、合规边界（如实说明）

| 事项 | 情况 |
|---|---|
| ICP 备案 | 用**公网 IP + 非 80/443 端口**访问，不触发备案拦截。**不需要备案** |
| 家庭宽带跑服务 | 运营商家宽条款通常禁止对外提供公共服务。小范围测试实务风险低 |
| 公安联网备案 | 严格来说公开信息服务应备案。10 人以内测试阶段实务风险低 |
| 何时必须转正 | 一旦用户量扩大、上应用商店、或涉及支付/敏感数据，需走 **域名 + ICP 备案 + HTTPS** 正规路线 |

**建议：** 测试阶段用穿透完全可行；正式运营前回到「升级阿里云 + 域名 + HTTPS + 备案」的路线。

## 八、下一步

**必须先做（否则不要公网暴露）：**

1. ✅ **改掉 JWT 默认密钥**（第三节）——这是硬性前置条件

**然后：**

2. 在阿里云安全组放行 **TCP 8080**（方案 B 再加 7000）
3. 服务器 `sshd_config` 开 `GatewayPorts clientspecified`（方案 A）或部署 frps（方案 B）
4. 在本机启动穿透客户端，设为开机自启
5. 用**已构建好的 APK** 真机验证

**顺带一提：** 原方案（后端跑阿里云）并未作废。如果测试期结束后要正式运营，升级到 4 GB 仍是干净解法——所有配置、数据、APK 都已就绪，一条命令即可恢复。
