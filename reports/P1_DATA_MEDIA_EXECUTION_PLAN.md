# P1 图片与关键数据可见执行计划

## 1. 阶段目标

本计划只执行精简总计划中的 P1：通过现有 Backend V1 API，让客户端稳定显示球员头像、球队 Logo、用户头像、内容封面，并补齐一场旗舰比赛及首页/数据中心所需的最小演示数据。

P1 完成后才允许制定并执行 P2 首页排布计划。本阶段不以视觉重构为目标，只处理“数据存在、接口返回、媒体可访问、客户端可呈现”的完整链路。

## 2. 阶段边界

### 2.1 纳入范围

- 后端公开媒体访问链路与 Flutter 媒体 URL 解析/渲染链路；
- 已有内容和本阶段新发布内容的封面显示；
- 2 支重点球队及每队至少 18 名球员；
- 1 场可从客户端正常进入的已结束旗舰比赛；
- 旗舰比赛阵容、事件、球队统计、球员统计和评分；
- 首页 8—12 条可展示内容及必要作者、评论和关联；
- 至少 1 个联赛、1 个杯赛的赛季、阶段、赛程、积分及榜单数据；
- P1 对应的 SQL 校验、API smoke、Flutter 定向测试和少量设备截图。

### 2.2 明确不纳入

- 首页推荐、资讯、比赛卡片的布局和视觉重做；
- 数据中心、球队、球员、比赛详情的整体样式对齐；
- 杯赛淘汰树入口或完整淘汰树后端模型；
- 手机验证码、一键手机号登录、微信登录；
- 私信、聊天、IM、WebSocket、Push；
- 无关重构、依赖升级、全仓格式化、全量回归和 60 张原型截图验收。

若执行中发现上述范围外问题，只记录到 P1 剩余问题，不顺手实现。

## 3. 模块划分与顺序

| 顺序 | 模块 | 核心结果 | 依赖 |
| ---: | --- | --- | --- |
| P1-M1 | 媒体显示闭环 | 头像、队徽、已有/新发布内容封面真实可见 | 无 |
| P1-M2 | 旗舰比赛与足球数据 | 2 队阵容及 1 场完整比赛可由现有 API 呈现 | M1 |
| P1-M3 | 首页内容与轻量互动数据 | 首页和关联详情有合理内容密度及可用封面 | M1；可与 M2 使用同一对象 |
| P1-M4 | P1 联调验收 | 数据、API、客户端证据闭环 | M1—M3 全部完成 |

模块必须按顺序验收。当前模块未完成时，只修复当前模块，不提前进入下一个模块。

## 4. 全阶段共同约束

### 4.1 数据安全

- 数据库 `south_stand` 及相关表由后端仓库 `D:\Football-APP` 管理，SQL 只提交到后端仓库；
- 执行前记录目标 ID、自然键、`source`、行数和引用关系；
- 优先补齐现有 DEMO 对象，避免创建重复球队、球员、比赛或用户；
- 只允许定向修改归属明确的 DEMO 数据；非 DEMO 和真实用户数据不得覆盖；
- 新增 seed 与 validator 使用 P1 独立命名和来源标记，必须幂等并可定向回滚；
- 禁止 `TRUNCATE`、全表 DELETE、`reset-dev` 和重新导入覆盖式历史 seed；
- 若保留 ID 区间已有非 DEMO 数据或自然键归属不清，立即停止该写入并报告冲突；
- 保护后端已有未提交文件，尤其不得覆盖 `scripts/sql/seed-f14-player-detail.sql`。

### 4.2 API 与前端约束

- 以现有 Controller、VO/DTO、前端 API/Repository 模型为准，不新增便利接口或虚构字段；
- P1 默认不新增数据库 migration；现有表能表达需求时只做增量数据和缺陷修复；
- 保留 `Result`、`PageResult`、分页、nullable 和枚举语义；
- 前端只允许修复媒体 URL、媒体渲染及发布封面链路，不修改页面构图；
- 不在 Widget 中硬编码球队、球员、比分、内容或图片 URL；
- 不为 SVG 显示新增依赖，P1 优先提供 PNG/JPG/WebP；
- 媒体失败占位必须保留，但正常 DEMO 数据不得主要依赖占位。

### 4.3 测试边界

- 每个模块只运行该模块的 SQL 校验、相关后端测试、相关 Flutter 测试和必要 API smoke；
- 不运行无关模块测试，不做全仓测试、全量截图或 P2/P3 视觉验收；
- Flutter 静态检查优先限定到 P1 修改文件/目录；只有共享网络或媒体组件改动影响面无法局部判断时，才在 P1-M4 运行一次完整 `flutter analyze`；
- 所有真实数据写入和客户端截图均使用同一开发数据库、同一后端版本和同一 Flutter 构建配置。

## 8. P1-M4：阶段联调验收

### 8.1 模块目标

只验证 P1 的数据与媒体链路，形成可供 P2 使用的稳定基线，不修改首页或详情页面视觉。

### 8.2 验收流程

P1-M4 分为三个验收模块和一个报告收口，按 M4-A → M4-B → M4-C → M4-D 顺序执行。M4 只负责收口；发现实现缺陷时退回对应模块做最小修复，不直接扩张为新功能。

#### P1-M4-A：数据与 API 联合验收

1. 核对前后端工作区，确认 M1—M3 产物齐全且没有覆盖用户已有改动；列出 P1 实际变更文件和目标 DEMO ID。
2. 记录三批 seed 执行前的目标表行数及非 DEMO 基线。在同一开发数据库按 M1 → M2 → M3 顺序执行 seed 和 validator，再完整重复一次；第二次不得新增重复数据或改变非目标数据。
3. 检查三份 rollback 只命中各自 source/ID/自然键范围；不得为了证明脚本存在而在当前工作数据库执行回滚。
4. 对以下现有接口做代表性 smoke：
   - 推荐 Feed、资讯 Feed、内容详情、评论；

#### P1-M4-B：用户内容分页契约复核

1. 使用同一登录账号请求 `/api/app/users/me/contents?pageNum=1&pageSize=10`，保存完整原始 JSON，确认读取的是 `data.records`、`data.total`、`data.pages`、`data.pageNum` 和 `data.pageSize`，先排除 smoke 脚本取错层级。
2. 将响应与该用户可见内容的数据库计数对照：records 非空时 `total` 必须不小于 records 数量，`pages` 必须等于向上取整结果。
3. 若原始响应正确，只修正旧报告或 smoke 解析，不修改后端。
4. 若原始响应确实为 records 非空但 `total/pages=0`，只检查用户内容分页的 Mapper/Page 调用、MyBatis 分页统计和 `PageResult.of` 入参；新增一个能够复现问题的后端定向测试并做最小修复。
