## 2. 已确认契约与能力边界

执行模型先复核，不发明字段或接口。现有契约已支持：

- `GET /api/app/contents/{contentId}`：标题、正文、作者、媒体、关系、点赞/评论/收藏计数和当前互动状态；
- `POST /api/app/likes/toggle`、`POST /api/app/favorites/toggle`；
- `GET /api/app/comments`、`GET /api/app/comments/{id}/replies`；
- `POST /api/app/comments`、`POST /api/app/comments/{id}/likes/toggle`、`DELETE /api/app/comments/{id}`；
- `GET /api/app/users/{userId}/profile`、`POST/DELETE /api/app/users/{userId}/follow`。

不得给内容详情 DTO 增加虚构的 `followed` 字段；作者关注状态应通过现有用户资料和关注接口取得。评论契约只支持文本及 `replyToUserId`，不支持评论图片、专用表情包或真正的 @ 用户选择器，这些按钮不得伪实现。

当前没有微信、朋友圈、小红书、抖音、QQ 等直连分享 SDK，也没有公开 Web 内容 URL。分享层只展示真正可工作的“复制链接/路径”和“更多（系统分享）”等能力，不得放置无响应的第三方平台按钮。允许新增的唯一依赖是 `share_plus`；若仓库已有等价系统分享封装则必须复用，不重复引入。

补数规则：

- 使用新的明确 ID 段，例如媒体 `16100000000000601` 起、评论 `16400000000000601` 起；执行前先验证未占用，冲突时更换整个 VR6 预留段并记录 Manifest，禁止覆盖。

数据库变化用于原型展示，不要求新增表、字段、Mapper、Controller 或 Service。
