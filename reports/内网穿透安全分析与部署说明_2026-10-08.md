# 内网穿透安全分析 + 部署说明

> 日期：2026-10-08
> 场景：后端跑本机，通过阿里云服务器做反向隧道，供 < 10 名测试用户访问

---

## 一、直接回答：内网穿透会不会导致本机被攻击？

**分成两件事看，答案不一样：**

| 问题 | 答案 |
|---|---|
| 隧道本身会不会把本机/局域网暴露出去？ | **不会。** 它不是 VPN，只是把 **一个端口** 转发出去 |
| 会不会因为你后端被公网可达而被攻击？ | **会，风险真实存在。** 已实测发现 4 个问题，**其中 1 个严重，均已修复** |

**一句话：风险不在"隧道"，而在"后端暴露到公网"。** 隧道只是修了一条路，路上跑的是你后端的 API。

---

## 二、暴露面实测：什么出去了，什么没出去

隧道只转发 **8080 一个端口**。实测确认：

### ✅ 被暴露（仅这些）
- 后端 REST API（`/api/auth/**`、`/api/app/**` 等）
- 后端提供的静态图片资源

### ✅ 没有被暴露（实测确认）
| 服务 | 端口 | 绑定 | 是否可达 |
|---|---|---|---|
| MySQL | 3306 | 仅 127.0.0.1 | ❌ 不可达（且未转发） |
| Redis | 6379 | 仅 127.0.0.1 | ❌ 不可达（且未转发） |
| 本机 nginx / nacos / milvus 等 | 80 / 8848 / 19530… | 各自本地 | ❌ 不可达（未转发） |
| 本机文件系统 / 命令行 | — | — | ❌ 隧道不提供该能力 |
| 你局域网里的其他设备 | — | — | ❌ 不是网络桥接，无法横向进入 |

> 这一点很关键：**诸如 Tailscale / ZeroTier 这类"网络层"方案会把你整台机器接入一个虚拟内网**，风险面大得多。而反向隧道是**点对点单端口转发**，天然更安全。

## 三、实测发现的风险与修复情况

| # | 问题 | 严重度 | 状态 |
|---|---|---|---|
| 1 | **JWT 使用公开的默认密钥** → 任何人可伪造管理员令牌 | 🔴 **严重** | ✅ **已修复** |
| 2 | 后端监听 `0.0.0.0` → 同一 WiFi/局域网内设备可直连 | 🟡 中 | ✅ **已修复** |
| 3 | 接口文档匿名可读（`/v3/api-docs`、`/swagger-ui`） | 🟡 中 | ✅ **已修复** |
| 4 | 本机 11 个旧计划任务会用不安全配置重启后端 | 🟡 中 | ✅ **已禁用** |
| 5 | `/doc.html` 静态页外壳仍返回 200 | 🟢 低 | ⚠️ 数据源已失效，页面拿不到 API 清单 |

### 问题 1 详解（最严重）

后端此前由 `start-backend-detached.ps1` 启动，该脚本第 26 行把 JWT 密钥设成了硬编码的开发占位串：

```powershell
$env:JWT_SECRET = 'dev_only_change_me_jwt_secret_please_override_in_prod_2026'
```

**实测验证（修复前）**：用这个公开密钥伪造一个 `roleType=ADMIN` 的令牌，后端**接受并返回了管理员数据**。

**说明**：`application.yml:59` 里也有同样的默认值，属于代码层面的可改进项（建议后续去掉这个兜底默认值，改成不设就拒绝启动）。

**修复后实测**：同样的伪造令牌 → `{"code":40101,"message":"未登录"}`，**已拒绝**。

### 问题 2 详解

后端原先监听 `0.0.0.0:8080`，意思是**同一局域网里任何设备都能直接访问它**（咖啡馆 WiFi、办公室网络都算）。叠加问题 1，同网段的人就能拿到管理员权限。已改为只监听 `127.0.0.1`。

### 问题 5 说明

`knife4j.enable=false` 关掉了它的数据接口，但静态页外壳还在。由于 `/v3/api-docs` 已返回异常，这个页面**打不开任何 API 清单**，实际价值为零，风险很低。若要做到干干净净，可在隧道前加一层 Nginx 直接拒绝该路径。

## 四、本来就安全的部分（实测确认，含一处更正）

| 项目 | 实测结果 |

## 五、隧道特有的风险（与后端代码无关）

这两条是"暴露到公网"必然带来的，无法通过改配置消除：

### 1. 带宽被占满（最容易发生）

家庭宽带上行实测只有 **11.7 Mbps**。任何人都能用脚本狂刷你的接口，把你的上行占满，导致**真实用户在测试期间完全打不开 App**。

- 缓解：**只在测试时段开隧道**，测试完立即关掉；不要 7×24 挂着

### 2. 扫描与垃圾注册

公网 IP 一旦开放，通常**几小时内**就会开始收到自动化扫描。注册接口是开放的，可能被批量注册垃圾账号。

- 缓解：测试期结束后关闭隧道；上线前给注册接口加验证码/限流

## 六、不会发生的风险（澄清常见误解）

| 误解 | 实际 |
|---|---|
| "穿透会把我整个内网暴露" | ❌ 只是单端口转发，不做网络桥接 |
| "别人能通过隧道访问我的其他电脑" | ❌ 隧道终点是本机 127.0.0.1:8080，无法横向移动 |
| "服务器被人拿下就能进我内网" | ⚠️ 已加固：sshd 设了 `PermitListen 8080`，**只允许转发 8080**，其他端口一律拒绝 |
| "隧道加了延迟所以更危险" | ❌ 延迟与安全无关（实测 0.12 秒） |

## 七、最坏情况

唯一能让攻击"烧到本机"的路径是：**后端本身存在远程代码执行漏洞**（例如文件上传被解析执行）。那时攻击者可以在你的本机上执行任意代码。

当前实测：上传接口需要登录、限制扩展名（jpg/jpeg/png/webp/gif）和大小（10MB），风险可控。但这是唯一需要持续留意的方向——**后端应保持更新**。

## 九、部署与日常操作

### 启动顺序

```powershell
# 1) 启动后端（安全参数已内置）
powershell -ExecutionPolicy Bypass -File D:\Football-APP\scripts\windows\start-backend-secure.ps1

# 2) 启动隧道（断线自动重连，Ctrl+C 停止）
powershell -ExecutionPolicy Bypass -File D:\Football-APP\scripts\windows\start-tunnel.ps1
```

### 停止（测试结束后务必执行）

```powershell
# 停隧道 = 立刻切断公网入口
Get-Process ssh -ErrorAction SilentlyContinue | Stop-Process -Force
```

### 需要你在阿里云控制台做的一步

**安全组放行 TCP 8080**（目前仍被拦截，外部还访问不到）：

> 控制台 → 网络与安全 → 安全组 → 配置规则 → 入方向 → 添加
> 协议 TCP，端口 **8080**，授权对象 `0.0.0.0/0`（或只填你自己的公网 IP 更安全）

### APK

已构建的 Release APK 直接指向 `http://8.138.118.219:8080`，且明文 HTTP 白名单已放行该 IP —— **无需改动即可使用**。

## 十、结论

- **隧道方式本身是安全的**：只转发一个端口，不暴露本机其他服务，不暴露局域网
- **但暴露后端带来了真实风险**，其中"公开默认 JWT 密钥"是严重级别，**已修复并实测验证**
- **最大的残余风险是带宽被刷**（家庭上行只有 11.7 Mbps），属于测试期可接受但需注意的问题
- **建议**：测试期随用随开，用完关隧道；正式运营时改回"升级阿里云 + 域名 + HTTPS + 备案"的正规路线
