## 3. M1：SQL 可逆性与数据所有权闭环

### 工作

1. 为 M1 Seed 的每个被改字段建立逐项清单：表、主键、执行前值、执行后值、归属依据和回滚谓词。
2. 补齐 `content_media.media_url`、`content_media.thumbnail_url`、`content_block.media_url`、遗漏球员头像和遗漏用户头像的 Rollback。
3. Rollback 必须仅在字段仍等于 VR14 写入值时恢复，避免覆盖后续合法修改；不得用宽泛范围无条件覆盖。
4. 对 M2 热度目标增加固定 ID/来源/作者等所有权校验和期望数量断言。不能证明为 DEMO 的记录不得修改。
5. M2 Rollback 必须恢复已核实的执行前值；若无法可靠重建原值，先制作受控快照或把该记录移出 Seed，不能用推测公式宣称可回滚。
6. Validator 增加 Seed 后状态、Rollback 后状态、非目标零变化和目标数量断言；Manifest 准确写明所有实际影响。

### 验证顺序

在可恢复的本地 DEMO 数据库执行：

1. 只读前置所有权检查；
2. Seed → Validator；
3. Seed 再跑 → Validator，验证幂等；
4. Rollback → 回滚 Validator，验证所有目标字段恢复；
5. Seed → Validator，恢复供客户端验收使用的目标状态。

不得删除、覆盖或回滚非 VR14/P1/VR9/VR11 专属 DEMO 数据。

## 4. M2：首页首屏一比一返修

### 工作

1. 以 `首页.png` 的可见首屏为验收对象，而不是以长列表中“最终能找到某卡”为验收对象。
2. 标准宽度首屏必须呈现与原型对应的业务组合和视觉重心：顶部紧凑比赛卡、图文内容、转会/动态、评分、积分/排名与讨论；每类使用现有专用卡，不全部套成帖子卡。
3. 保持真实 Feed 数据和现有卡片点击语义。允许对已确认的 DEMO 记录做窄范围权重/关联调整，但不得硬编码生产卡片、固定实体 ID 或客户端假数据。
4. 调整双列布局的卡宽、首卡位置、图片比例、标题行数、元信息行和列间节奏；减少同一球场图片在首屏重复造成的占位感。
5. 顶部球队快捷项不得裁掉完整队名或菜单入口；若空间不足，按原型采用横向滚动/省略规则并提供可点击完整项。
6. 推荐、资讯、关注、球队筛选及卡片跳转必须保持可用。

### 必测断言

- 使用真实 API fixture/录制响应，不手工虚构“必然有全部卡”的列表；
- 断言首屏第一张卡的业务类型、主要卡类型集合和相对纵向位置；
- 断言标准宽度下左右列卡宽、列间距和首卡顶部误差；
- 断言 360dp 与 140% 字体下加载完成后无 overflow、底栏遮挡和顶部截断；
- 不允许把 `pageSize == 30` 当作视觉验收断言。
