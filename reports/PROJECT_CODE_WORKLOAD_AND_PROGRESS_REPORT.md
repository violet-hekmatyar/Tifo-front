# 南看台项目工作量与功能进度汇报

> 本报告用于向导师、老板或项目负责人说明：近期做了多少工作、产品现在能做什么、还缺什么，以及哪些足球功能必须先获得真实数据。

## 1. 一页总结

南看台已经不是只有界面图片的原型。目前已经具备三个可以协同工作的部分：

| 产品组成 | 面向谁 | 当前情况 |
|---|---|---|
| Flutter 手机客户端 | 普通球迷用户 | 已完成登录、首页、发帖互动、基础足球数据和个人中心主流程 |
| Vue 管理后台 | 内部管理员 | 已完成管理员登录、权限控制和后台框架，具体管理页面仍需继续开发 |
| Java 后端服务 | 手机端和后台共同使用 | 已支持账号、关注、内容、评论、基础足球数据、文件和用户中心 |

用户目前已经可以完成以下完整流程：

```text
注册/登录
  → 选择主队、关注球队和球员
  → 浏览首页内容和比赛
  → 查看帖子、球队、球员和比赛详情
  → 发帖、上传图片、评论、回复、点赞、收藏
  → 查看个人主页、发布、收藏、评论、关注和粉丝
```

项目当前更准确的定位是：

| 判断 | 结论 |
|---|---|
| 能否演示完整的普通用户主流程 | 可以 |
| 是否已经达到完整商业产品水平 | 还没有 |
| 当前最大的功能缺口 | 专业足球榜单/统计、消息通知、后台业务页面 |
| 当前最大的外部依赖 | 稳定、合法、持续更新的真实足球数据源 |
| 当前最应该先做什么 | 补齐文章、我的点赞和产品规则，再确定真实足球数据来源 |

## 5. 哪些功能必须依赖真实数据

当前本地后端有联赛、球队、球员、比赛和事件数据，可以用于开发和演示页面，但其中存在演示内容，不能直接当成正式比赛事实。此前的数据审计已经发现赛季、教练、球员所属球队和部分比赛记录与现实不一致。

### 数据依赖分级

| 数据类型 | 示例 | 能否自己在系统内产生 | 正式上线建议 |
|---|---|:---:|---|
| 用户社区数据 | 发帖、评论、点赞、收藏、关注 | 可以 | 由用户操作自然产生，不需要足球数据供应商 |
| 基础足球资料 | 联赛、球队、球员、Logo、球场、教练 | 可以人工录入，但维护量大 | 使用官方来源或授权数据源，并定期更新 |
| 赛程和比分 | 比赛时间、状态、比分、事件 | 不能稳定靠人工维护 | 必须接入持续更新的赛事数据源 |
| 积分榜和榜单 | 联赛排名、射手榜、助攻榜 | 不能只靠前端计算 | 需要可靠数据源和后端统计规则 |
| 球队阵容 | 当前球员、号码、位置、转会变化 | 人工维护容易过期 | 需要持续更新的阵容数据 |
| 球队/球员统计 | 射门、传球、抢断、评分等 | 无法从现有基础数据推导 | 通常需要更高级、可能收费的数据套餐 |
| 历史和生涯 | 球员历年数据、球队荣誉 | 可以一次性整理，但工作量大 | 需要历史数据库或可靠资料来源 |
| 媒体评分 | 专业媒体赛后评分 | 不能自行声称为媒体评分 | 需要获得数据使用许可 |
| 视频集锦 | B站、微博、YouTube 或版权方视频 | 不能随意复制 | 必须确认嵌入规则、平台条款和版权 |

### 真实足球数据到位前，前端不能“自己补”的功能

| 功能 | 为什么不能只改页面 |
|---|---|
| 积分榜 | 页面无法知道真实积分、扣分和同分排序规则 |
| 球员榜/球队榜 | 当前后端没有完整赛季统计数据 |
| 球队阵容 | 现有底层关系不足以保证名单完整和最新 |
| 球员赛季统计和生涯 | 需要每场出场和历史赛季数据 |
| 比赛阵容和详细统计 | 需要首发、替补和比赛过程统计 |
| 媒体评分 | 需要合法的数据提供方 |
| 实时比分和事件 | 需要持续推送或高频更新的数据服务 |

## 7. 下一阶段建议

### 第一优先：把现有主流程补完整

| 功能 | 为什么优先 | 是否需要外部足球数据 |
|---|---|:---:|
| 我的点赞列表 | 个人中心当前有明显缺口 | 否 |
| 真正的图文混排文章 | 原需求明确区分帖子和文章 | 否 |
| 球队最多关注数量 | 当前需求和后端规则冲突 | 否，但需要产品确认 |
| 发布时选择球队/球员/比赛 | 能提高内容归类和推荐准确性 | 基础实体需要真实数据 |
| 互关文案和关注确认 | 后端已支持，前端工作量较小 | 否 |
| 球队详情中的关联资讯 | 后端已有查询能力，可直接接入 | 否 |

### 第二优先：先解决真实足球数据来源

在开发积分榜、球员榜和详细统计前，需要先确认：

| 需要决定的问题 | 原因 |
|---|---|
| 使用哪家足球数据 API | 不同供应商覆盖赛事和字段不同 |
| 是否有费用预算 | 比分、阵容和高级统计通常按套餐收费 |
| 是否允许使用球队 Logo、球员头像 | 涉及商标、肖像或数据使用条款 |
| 更新频率 | 赛程、比分、转会和阵容需要持续更新 |
| 是否需要历史数据 | 球员生涯和球队荣誉需要多年数据 |
| 第一版支持哪些赛事 | 支持范围越大，成本和维护量越高 |

### 第三优先：建设专业足球功能

```text
赛季和积分榜
  → 球员榜、球队榜
  → 球队阵容和赛季统计
  → 球员比赛记录和生涯
  → 比赛阵容和详细统计
  → 用户评分和媒体评分
  → 首页增加榜单/评分卡片
```

### 第四优先：通知和后台业务

|---|---|
| 互动通知 | 先做评论、点赞、关注提醒和未读数 |

## 8. 需要负责人确认的四个决定

| 决定 | 不确认的影响 |
|---|---|
| 是否购买或接入足球数据服务 | 无法可靠完成积分榜、阵容和统计 |
| 第一版是否限制最多关注五支球队 | 前端需求和后端规则会继续冲突 |
| 第一版专业足球功能做到多深 | 会直接影响开发周期和数据费用 |
| 后台管理和消息通知哪个优先 | 两条工作线都未完成，需要明确资源顺序 |

## 9. 风险和说明

- 当前基础流程可演示，但本地足球数据包含演示记录，不能当作正式赛事事实。
- 足球功能越深入，对外部数据覆盖、实时性、费用和版权要求越高。
- 自动测试和联调已经覆盖大量流程，但手机端和浏览器仍需统一人工验收视觉效果。
- 代码由 Git 作者身份提交，其中可能包含 AI 辅助和框架生成内容，无法仅凭 Git 自动区分。
- 代码行数只用于描述工作规模，不等同于产品价值或代码质量。
